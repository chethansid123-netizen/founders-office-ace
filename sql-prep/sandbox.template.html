How SQL thinks

If you learn only one thing before the interview, learn this part. Almost every "why doesn't this work?" question has its answer here.

SQL is a description, not a set of steps

In Python or Java you tell the machine how to get the answer: loop over rows, keep a counter, append to a list. In SQL you describe what the answer looks like, and the database decides how to get it.

So stop thinking "for each row…". Start thinking "I have a table. I filter it. I fold it into groups. I filter the groups. I sort. I take the top N." Every query is that pipeline, in some combination.

The unit you work with is the result set: a table in, a table out. That is why a query can be nested inside another query — the inside one produces a table, and tables are what SQL consumes.

The logical order of execution — the single most useful thing you know

You write a query in one order. The database evaluates it in a different order. Nearly every beginner error comes from confusing the two.

You write it in this order
SELECT   ...
FROM     ...
WHERE    ...
GROUP BY ...
HAVING   ...
ORDER BY ...
LIMIT    ...
It runs in this order
1.  FROM         pick the starting table
2.  JOIN / ON    attach other tables, build the combined row set
3.  WHERE        throw away individual ROWS you don't want
4.  GROUP BY     fold the surviving rows into one row per group
5.  HAVING       throw away whole GROUPS you don't want
6.  SELECT       compute the output columns (and window functions)
7.  DISTINCT     remove duplicate output rows
8.  ORDER BY     sort the final rows
9.  LIMIT/OFFSET keep only a slice

Read that list top to bottom and three notorious interview questions answer themselves:

Why can't I use a SELECT alias in WHERE?
Because WHERE runs at step 3 and SELECT at step 6. When WHERE is evaluated the alias does not exist yet. But ORDER BY (step 8) runs after SELECT, which is exactly why ORDER BY my_alias is allowed.
Why is WHERE different from HAVING?
WHERE filters rows before grouping (step 3). HAVING filters groups after grouping (step 5). That is the whole difference. See Part 10.
Why can't I put a window function in WHERE?
Window functions are computed at step 6, inside SELECT. WHERE at step 3 runs earlier, so the value doesn't exist yet. Wrap the query in a CTE and filter outside. See Part 16.

Run this to see the pipeline in one query — each clause is labelled with the step it belongs to:

SELECT   c.country,                                  -- 6. computed last
         COUNT(*)        AS order_count,              -- 6.
         SUM(oi.line_total) AS revenue                -- 6.
FROM     orders o                                    -- 1. start here
JOIN     customers   c  ON c.cust_id  = o.cust_id    -- 2. attach
JOIN     order_items oi ON oi.order_id = o.order_id  -- 2. attach
WHERE    o.status = 'completed'                      -- 3. drop rows
GROUP BY c.country                                   -- 4. fold into groups
HAVING   SUM(oi.line_total) > 20000                  -- 5. drop groups
ORDER BY revenue DESC                                -- 8. alias IS allowed here
LIMIT    5;                                          -- 9. slice

Rows, columns, and "grain" — the word that saves you

Grain means: what does one row of this result represent? Say it out loud before you write anything.

Table / resultOne row means…
customersone customer
ordersone order
order_itemsone product line within one order
orders JOIN order_itemsone product line (the order columns now repeat)
GROUP BY countryone country

Interviewers listen for this. "This join takes me from order grain to line grain, so I need COUNT(DISTINCT o.order_id), not COUNT(*)" is the sentence that gets you hired.

The fan-out trap. Joining orders (48 rows) to order_items (119 rows) gives 119 rows. Any SUM of an order-level column is now counted once per line item — silently wrong. Run the query below and watch COUNT(*) disagree with COUNT(DISTINCT order_id).
SELECT COUNT(*)                    AS rows_after_join,   -- 119: line grain
       COUNT(DISTINCT o.order_id)  AS actual_orders      -- 48:  order grain
FROM   orders o
JOIN   order_items oi ON oi.order_id = o.order_id;

Syntax anatomy & punctuation

Where the commas go, when brackets are required, which quote means what. This is the part nobody teaches and everybody gets wrong under pressure.

The parts of a statement

SELECT   first_name, salary * 1.1 AS new_salary
--       └─────┬────┘ └──────┬─────┘    └────┬────┘
--          column        expression        alias
FROM     employees e
--       └───┬────┘ ┬
--          table   table alias
WHERE    salary > 100000 AND dept_id = 1;
--       └──────┬───────┘ └┬┘ └─────┬────┘
--           predicate    operator  predicate
  • Keyword — SELECT, FROM. Case-insensitive. Convention: UPPERCASE.
  • Identifier — a table or column name. Case-insensitive unless you double-quote it.
  • Literal — a fixed value: 'text', 42, TRUE, DATE '2024-01-01'.
  • Operator — =, <, +, ||, AND.
  • Expression — anything that computes to a value: salary * 1.1.
  • Predicate — an expression that evaluates to TRUE / FALSE / UNKNOWN.
  • Clause — a keyword and what follows it: the whole WHERE … chunk.

Commas: the rule that prevents half your syntax errors

Commas separate items in a list. Nothing else. They go between columns, between tables, between values, between GROUP BY / ORDER BY keys.

Never put a comma before the word that ends the list — no comma before FROM, before WHERE, before ). "Trailing comma before FROM" is the #1 typo in live interviews.
-- ✅ correct
SELECT a, b, c FROM t;
--       ↑  ↑ commas BETWEEN items, none before FROM

-- ❌ trailing comma
SELECT a, b, c, FROM t;          -- syntax error at or near "FROM"

-- ❌ missing comma  →  SQL reads "b c" as "column b aliased c"
SELECT a, b c FROM t;            -- no error! silently gives you 2 columns, not 3
The silent one. A missing comma usually does not error — SQL treats the next word as an alias. SELECT first_name last_name FROM employees returns one column called last_name holding first names. Run it and see.
SELECT emp_name  title   FROM employees LIMIT 3;   -- 1 column, aliased "title"

Never use a comma to join tables in modern SQL — write JOIN … ON … instead (see Part 12).

Quotes: three kinds, three meanings

The classic. WHERE city = "Mumbai" fails in Postgres with column "Mumbai" does not exist — double quotes made it an identifier. Data goes in single quotes. Always.

To put an apostrophe inside a string, double it: 'O''Brien'. Postgres also allows dollar quoting for messy text: $$O'Brien$$.

SELECT 'O''Brien' AS doubled, $$O'Brien$$ AS dollar_quoted;

Brackets: when they are required, when they are optional

Required:

  • Function calls — always, even with no arguments: NOW(), COUNT(*).
  • Around an IN list: WHERE status IN ('completed','refunded').
  • Around every subquery: WHERE id IN (SELECT …).
  • Around the column list in INSERT and CREATE TABLE.
  • Around the OVER (…) spec of a window function — even when empty: SUM(x) OVER ().

Optional but strongly advised: around mixed AND/OR, because AND binds tighter than OR:

-- These two return DIFFERENT results. Run it.
SELECT COUNT(*) AS without_brackets
FROM   orders
WHERE  status = 'completed' OR status = 'pending' AND channel = 'web';

SELECT COUNT(*) AS with_brackets
FROM   orders
WHERE (status = 'completed' OR status = 'pending') AND channel = 'web';
Habit worth building: whenever a WHERE mixes AND and OR, bracket the OR group. It costs two keystrokes and removes a whole class of bug.

Semicolons, comments, casing, whitespace

  • Semicolon ends a statement. Required when you send several statements at once.
  • Line comment: -- to end of line. Block comment: /* … */, and it nests.
  • Keywords are case-insensitive. select = SELECT.
  • Unquoted identifiers are folded to lower case in Postgres. MyTable becomes mytable. Only "MyTable" keeps its capitals — and then you must quote it everywhere, forever. Don't start.
  • String comparison IS case-sensitive: 'Mumbai' <> 'mumbai'. Use ILIKE or LOWER() to compare loosely.
  • Whitespace and newlines are free. Use them — indented SQL reads better and interviewers notice.
SELECT 'Mumbai' = 'mumbai'         AS exact_match,      -- false
       'Mumbai' ILIKE 'mumbai'     AS case_insensitive,  -- true
       LOWER('Mumbai') = 'mumbai'  AS lowered;           -- true

Casting between types

Syntax

expression::type             -- PostgreSQL shorthand

       '42'::integer                 AS pg_cast,
       '2024-03-15'::date            AS to_date,
       123.789::numeric(6,1)         AS rounded,
       7 / 2                         AS integer_division,   -- 3  ← the trap

Integer division truncates. 7 / 2 is 3, not 3.5, because both sides are integers. This silently destroys percentages and averages. Cast one side to numeric first. Interviewers absolutely test this.

DDL — creating and changing tables

DDL = Data Definition Language. It defines the shape of the data. Everything here is runnable; the demo tables are named demo_* so they never disturb the practice data. Hit Reset database in the console any time.

CREATE TABLE

Syntax
CREATE TABLE [IF NOT EXISTS] table_name (
    column_name  data_type  [column_constraints…],
    column_name  data_type  [column_constraints…],
    …                                              -- ← no comma after the LAST column
    [, CONSTRAINT name  table_level_constraint ]
);

Two ways to write a constraint. Column-level sits on one column. Table-level sits at the end and can span several columns — that is the only way to write a composite key.

Example — every constraint type, once
DROP TABLE IF EXISTS demo_enrolments;
DROP TABLE IF EXISTS demo_students;

CREATE TABLE demo_students (
    student_id  integer      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    full_name   text         NOT NULL,
    email       text         NOT NULL UNIQUE,
    age         integer      CHECK (age >= 16),
    country     text         NOT NULL DEFAULT 'India',
    created_at  timestamptz  NOT NULL DEFAULT now()
);

CREATE TABLE demo_enrolments (
    student_id  integer NOT NULL REFERENCES demo_students(student_id) ON DELETE CASCADE,
    course_code text    NOT NULL,
    grade       numeric(4,1) CHECK (grade BETWEEN 0 AND 100),
    PRIMARY KEY (student_id, course_code)        -- COMPOSITE key: table-level only
);

SELECT 'created' AS status;

PRIMARY KEY vs UNIQUE — a guaranteed interview question. A primary key is UNIQUE + NOT NULL, and a table has at most one. A UNIQUE constraint permits NULLs (and in Postgres, many NULLs, because NULL <> NULL), and you can have as many as you like.

Prove the NULL half of that claim:

DROP TABLE IF EXISTS demo_uniq;
CREATE TABLE demo_uniq (code text UNIQUE);
INSERT INTO demo_uniq VALUES (NULL), (NULL), (NULL);   -- three NULLs, no error
SELECT COUNT(*) AS null_rows_allowed FROM demo_uniq;

Foreign keys and referential actions

A foreign key says "this value must exist over there". The referential action says what happens when the parent row is deleted or updated.

FOREIGN KEY (child_col) REFERENCES parent_table(parent_col)
    ON DELETE { NO ACTION | RESTRICT | CASCADE | SET NULL | SET DEFAULT }
    ON UPDATE { … same options … }

Say this out loud in the interview: "I'd use ON DELETE CASCADE for order_items, because a line item has no meaning without its order. I'd use ON DELETE RESTRICT for products, because deleting a product that has been sold would destroy history."

DML — inserting and changing data

DML = Data Manipulation Language. It changes the rows, not the shape.

INSERT

Syntax
-- one row
INSERT INTO t (col1, col2) VALUES (v1, v2);

-- many rows in ONE statement (far faster than many statements)
INSERT INTO t (col1, col2) VALUES (v1, v2), (v3, v4), (v5, v6);

-- from a query
INSERT INTO t (col1, col2) SELECT a, b FROM other WHERE …;

-- get back what was actually written (PostgreSQL)
INSERT INTO t (col1) VALUES (v1) RETURNING *;
Always name the columns. INSERT INTO t VALUES (…) relies on column order, so it breaks silently the day someone adds a column. Naming them is the professional habit.
INSERT INTO demo_students (student_name, email, age, country)
VALUES ('Aarav Singh',  'aarav@ex.com',  22, 'India'),
       ('Bianca Rossi', 'bianca@ex.com', 25, 'Italy'),
       ('Chen Wei',     'chen@ex.com',   19, 'China')
RETURNING student_id, student_name, created_at;

UPDATE

UPDATE t
SET    col1 = expr1,
       col2 = expr2          -- ← commas BETWEEN assignments
WHERE  condition             -- ← omit this and you update EVERY ROW
RETURNING *;

-- update using another table (PostgreSQL)
UPDATE t
SET    col = o.val
FROM   other o
WHERE  o.id = t.id;
The career-limiting mistake. UPDATE t SET x = 1; with no WHERE updates every row in the table. Write the WHERE first, then go back and write the SET. Better: run it as a SELECT first to see what you'd hit.
-- Step 1: SEE what you are about to change
SELECT student_id, student_name, age FROM demo_students WHERE country = 'India';

-- Step 2: change it
UPDATE demo_students
SET    age = age + 1
WHERE  country = 'India'
RETURNING student_id, student_name, age;

DELETE

DELETE FROM t WHERE condition RETURNING *;

-- delete using another table (PostgreSQL)
DELETE FROM t USING other o WHERE o.id = t.id AND o.flag;
DELETE FROM demo_students WHERE age < 20 RETURNING student_name, age;

UPSERT — INSERT … ON CONFLICT

"Insert it; if it already exists, update it instead." Postgres spells this ON CONFLICT.

INSERT INTO t (key, val) VALUES (…)
ON CONFLICT (key) DO NOTHING;

INSERT INTO t (key, val) VALUES (…)
ON CONFLICT (key) DO UPDATE
SET   val = EXCLUDED.val          -- EXCLUDED = the row you TRIED to insert
WHERE t.val IS DISTINCT FROM EXCLUDED.val;
EXCLUDED is a special alias for the row that failed to insert. Remembering that name is the whole trick to this question.
DROP TABLE IF EXISTS demo_stock;
CREATE TABLE demo_stock (sku text PRIMARY KEY, qty integer NOT NULL);
INSERT INTO demo_stock VALUES ('A1', 10), ('B2', 5);

-- A1 exists → its qty is ADDED to. C3 does not exist → inserted.
INSERT INTO demo_stock (sku, qty) VALUES ('A1', 4), ('C3', 7)
ON CONFLICT (sku) DO UPDATE SET qty = demo_stock.qty + EXCLUDED.qty
RETURNING sku, qty;

MERGE — the ANSI standard version

Postgres 15+ supports MERGE. It is what SQL Server and Oracle have always used, and it is the standard answer for "how do you do an upsert?" outside Postgres.

MERGE INTO target t
USING source s ON t.key = s.key
WHEN MATCHED  AND condition THEN UPDATE SET col = s.col
WHEN MATCHED  THEN DELETE
WHEN NOT MATCHED THEN INSERT (key, col) VALUES (s.key, s.col);
MERGE INTO demo_stock t
USING (VALUES ('B2', 100), ('D4', 42)) AS s(sku, qty)
ON t.sku = s.sku
WHEN MATCHED     THEN UPDATE SET qty = s.qty
WHEN NOT MATCHED THEN INSERT (sku, qty) VALUES (s.sku, s.qty);

SELECT * FROM demo_stock ORDER BY sku;

SELECT & FROM

The complete SELECT skeleton

Every clause is optional except SELECT. When present, they must appear in this written order:

WITH     cte_name AS ( … )              -- Part 15
SELECT   [DISTINCT | DISTINCT ON (…)]
         expression [AS alias], …
FROM     table [alias]
         [JOIN other ON …]              -- Part 12
WHERE    row_condition                  -- Part 06
GROUP BY grouping_columns               -- Part 09
HAVING   group_condition                -- Part 10
WINDOW   w AS ( … )                     -- Part 16
ORDER BY sort_columns [ASC|DESC] [NULLS FIRST|LAST]   -- Part 11
LIMIT    n  OFFSET m;                   -- Part 11

The SELECT list

SELECT emp_name,                          -- a column
       salary,                            -- another column
       salary * 12          AS annual,    -- an expression, aliased
       'INR'                AS currency,  -- a constant
       UPPER(title)         AS title_caps,-- a function call
       salary / 12.0        AS monthly    -- note the .0 → decimal division
FROM   employees
LIMIT  5;

Aliases. AS is optional but write it — salary*12 annual works and reads like a mistake. Use double quotes only if the alias needs spaces or capitals: AS "Annual Salary".

SELECT * in an interview. Fine while exploring. In a final answer it signals carelessness: it breaks when columns change, ships data you don't need, and prevents index-only scans. Name your columns.

DISTINCT — and Postgres's DISTINCT ON

DISTINCT de-duplicates the whole output row, not one column. It runs at step 7, after SELECT.

SELECT DISTINCT country            FROM customers ORDER BY country;
SELECT DISTINCT country, segment   FROM customers ORDER BY 1,2;  -- distinct PAIRS
SELECT COUNT(DISTINCT country) AS n_countries FROM customers;
DISTINCT ON is Postgres-only and extremely useful. It keeps the first row per group given an ORDER BY. It is the shortest possible "most recent record per customer" — no window function needed. The leading ORDER BY columns must match the DISTINCT ON columns.
-- Most recent order per customer, in 4 lines
SELECT DISTINCT ON (cust_id)
       cust_id, order_id, order_date, status
FROM   orders
ORDER  BY cust_id, order_date DESC, order_id DESC;

FROM — where rows come from

A FROM source can be a table, a view, a subquery, a CTE, a function, or a literal list of values.

-- 1. a table, with an alias
SELECT e.emp_name FROM employees e LIMIT 3;

-- 2. a derived table (subquery) — the alias is MANDATORY
SELECT t.dept_id, t.headcount
FROM  (SELECT dept_id, COUNT(*) AS headcount FROM employees GROUP BY dept_id) AS t
ORDER BY t.headcount DESC;

-- 3. a literal VALUES list, used like a table
SELECT * FROM (VALUES ('a', 1), ('b', 2)) AS v(letter, num);

-- 4. a set-returning function
SELECT * FROM generate_series(1, 5) AS n;
"subquery in FROM must have an alias" is one of the most common Postgres errors. Every derived table needs a name. Add AS t.

AND / OR / NOT and precedence

AND is evaluated before OR. Always bracket a mixed condition.

-- "Enterprise customers, plus anyone at all from Germany"
SELECT cust_name, segment, country
FROM   customers
WHERE  segment = 'Enterprise' OR country = 'Germany'
ORDER  BY country;

-- "Customers who are Enterprise AND from either India or the UK"
SELECT cust_name, segment, country
FROM   customers
WHERE  segment = 'Enterprise'
  AND (country = 'India' OR country = 'UK')
ORDER  BY country;

NULL & three-valued logic

NULL is where confident candidates fall over. It is not zero and not an empty string — it means unknown. Once you accept that, every rule below follows.

Any comparison with NULL yields UNKNOWN

SELECT NULL = NULL      AS eq,        -- NULL (not true!)
       NULL <> NULL     AS neq,       -- NULL
       NULL > 5         AS gt,        -- NULL
       NULL + 10        AS arithmetic,-- NULL
       'abc' || NULL    AS concat,    -- NULL — one NULL poisons the string
       NULL IS NULL     AS is_null;   -- TRUE  ← the ONLY way to test
The rule: use IS NULL / IS NOT NULL. = NULL is never true and is always a bug.

The NOT IN + NULL trap — the most famous one of all

If the list inside NOT IN contains a single NULL, the whole predicate becomes UNKNOWN for every row, and you get zero rows back.

-- employees.dept_id contains one NULL (the CEO), so this returns NOTHING:
SELECT COUNT(*) AS with_not_in
FROM   departments
WHERE  dept_id NOT IN (SELECT dept_id FROM employees);

-- NOT EXISTS is NULL-safe and gives the right answer (2 empty departments):
SELECT COUNT(*) AS with_not_exists
FROM   departments d
WHERE  NOT EXISTS (SELECT 1 FROM employees e WHERE e.dept_id = d.dept_id);
Why. x NOT IN (1, 2, NULL) expands to x<>1 AND x<>2 AND x<>NULL. That last term is UNKNOWN, and TRUE AND UNKNOWN = UNKNOWN, which WHERE discards. Fix: use NOT EXISTS, or add WHERE dept_id IS NOT NULL to the subquery.

CASE — SQL's if/else

Two forms. Searched (any condition) and simple (equality against one expression).

Syntax
-- searched: use this one, it does everything
CASE WHEN condition1 THEN result1
     WHEN condition2 THEN result2
     ELSE fallback                  -- omit ELSE and unmatched rows get NULL
END

-- simple: shorthand for equality only
CASE expression
     WHEN value1 THEN result1
     WHEN value2 THEN result2
     ELSE fallback
END

CASE works anywhere an expression works: SELECT, WHERE, ORDER BY, GROUP BY, and inside an aggregate.

SELECT emp_name, salary,
       CASE WHEN salary >= 175000 THEN 'executive'
            WHEN salary >= 130000 THEN 'senior'
            WHEN salary >= 100000 THEN 'mid'
            ELSE 'junior'
       END AS band,
       CASE title WHEN 'CEO' THEN 'founder' ELSE 'staff' END AS kind
FROM   employees
ORDER  BY salary DESC;
Conditional aggregation — CASE inside SUM/COUNT is how you pivot rows into columns. This single pattern answers a huge share of analyst interview questions. See Part 17.
SELECT c.country,
       COUNT(*)                                                AS all_orders,
       COUNT(*) FILTER (WHERE o.status = 'completed')           AS completed,   -- Postgres
       SUM(CASE WHEN o.status = 'cancelled' THEN 1 ELSE 0 END)  AS cancelled,   -- portable
       ROUND(100.0 * COUNT(*) FILTER (WHERE o.status='completed') / COUNT(*), 1) AS pct_completed
FROM   orders o
JOIN   customers c ON c.cust_id = o.cust_id
GROUP  BY c.country
ORDER  BY all_orders DESC;
FILTER (WHERE …) vs CASE. They do the same job. FILTER is cleaner and is standard SQL, but MySQL and SQL Server don't have it — so know the CASE form too, and say so: "I'd use FILTER in Postgres, CASE if this has to be portable."

GROUP BY & aggregate functions

An aggregate takes many rows and returns one value. GROUP BY says which rows get folded together.

The rule that answers your question directly

THE RULE. The moment you use SUM, COUNT, AVG, MIN or MAX alongside any ordinary column, every ordinary column in your SELECT must also appear in GROUP BY.

Put plainly: every column in the SELECT list is either aggregated, or it is in the GROUP BY. There is no third option.
SELECT   dept_id,        -- ordinary column  → MUST be in GROUP BY
         COUNT(*),       -- aggregated       → must NOT be in GROUP BY
         AVG(salary)     -- aggregated       → must NOT be in GROUP BY
FROM     employees
GROUP BY dept_id;        -- ← exactly the ordinary columns, nothing else

Break the rule and Postgres tells you precisely what is wrong. Run this to see the error text — learn to recognise it, because you will trigger it live:

-- ERROR: column "employees.emp_name" must appear in the GROUP BY clause
--        or be used in an aggregate function
SELECT dept_id, emp_name, COUNT(*)
FROM   employees
GROUP  BY dept_id;
Why the rule exists. A group of 6 engineers folds into one row. If you ask for emp_name, which of the 6 names should the database print? There is no defensible answer, so it refuses. MySQL historically guessed (returning an arbitrary name) — which is exactly why that behaviour is now off by default. If asked, say: "Postgres rejects it; older MySQL silently picked one, which hides bugs."

Aggregating with no GROUP BY collapses the entire table to a single row:

SELECT COUNT(*) AS employees, AVG(salary)::numeric(10,2) AS avg_salary
FROM   employees;   -- one row, whole table

GROUPING SETS, ROLLUP and CUBE — subtotals in one pass

These produce several grouping levels in a single query. ROLLUP gives a hierarchy of subtotals plus a grand total; CUBE gives every combination.

GROUP BY ROLLUP(a, b)        ≡ GROUPING SETS ((a,b), (a), ())
GROUP BY CUBE(a, b)          ≡ GROUPING SETS ((a,b), (a), (b), ())
GROUP BY GROUPING SETS (…)   -- you list exactly the levels you want
GROUPING(col)                -- 1 when this row is a subtotal for that column, else 0
SELECT COALESCE(c.country, '— ALL COUNTRIES —') AS country,
       COALESCE(o.status,  '— all statuses —')  AS status,
       COUNT(*)        AS orders,
       GROUPING(c.country) AS is_country_total,
       GROUPING(o.status)  AS is_status_total
FROM   orders o
JOIN   customers c ON c.cust_id = o.cust_id
GROUP  BY ROLLUP(c.country, o.status)
ORDER  BY is_country_total, c.country, is_status_total, o.status;
Why GROUPING() matters. A subtotal row has NULL in the rolled-up column — but so does a genuine NULL in the data. GROUPING() is the only way to tell them apart.

HAVING

WHERE filters rows. HAVING filters groups.

SELECT   group_cols, AGG(x)
FROM     t
WHERE    row_level_condition        -- runs BEFORE grouping, cannot see aggregates
GROUP BY group_cols
HAVING   AGG(x) > threshold         -- runs AFTER grouping, CAN see aggregates
ORDER BY …
WHEREHAVING

Both in one query — this is the shape interviewers want to see:

SELECT   c.country,
         COUNT(DISTINCT o.order_id)   AS orders,
         SUM(oi.line_total)           AS revenue
FROM     orders o
JOIN     customers   c  ON c.cust_id  = o.cust_id
JOIN     order_items oi ON oi.order_id = o.order_id
WHERE    o.status = 'completed'        -- ROW filter: drop non-completed orders first
GROUP BY c.country
HAVING   COUNT(DISTINCT o.order_id) >= 3   -- GROUP filter: keep busy countries
     AND SUM(oi.line_total) > 10000
ORDER BY revenue DESC;
Don't put a row condition in HAVING. HAVING o.status = 'completed' may run, but it filters after the database has already grouped every row — slower, and it only works if status is in the GROUP BY. Rule: if the condition mentions no aggregate, it belongs in WHERE.
The one-line answer to "WHERE vs HAVING?"
"WHERE filters rows before they're grouped; HAVING filters groups after. So aggregates can only be used in HAVING. If my condition has no aggregate in it, I put it in WHERE, because filtering earlier is cheaper."

ORDER BY, LIMIT & OFFSET

ORDER BY

ORDER BY expr [ASC | DESC] [NULLS FIRST | NULLS LAST],
         expr2 [ASC | DESC], …
  • ASC is the default; you rarely write it.
  • Postgres default: ASC → NULLs last; DESC → NULLs first.
  • You may sort by a SELECT alias, a column not in the SELECT list, an expression, or an ordinal.
  • Sorting is the last thing that happens (step 8) — so aliases work here and nowhere earlier.
SELECT cust_name, city, segment
FROM   customers
ORDER  BY segment ASC,
          city DESC NULLS LAST,     -- push the unknown cities to the bottom
          cust_name;
-- custom ordering with CASE: put statuses in business order, not alphabetical
SELECT order_id, status
FROM   orders
ORDER  BY CASE status WHEN 'pending'   THEN 1
                      WHEN 'completed' THEN 2
                      WHEN 'refunded'  THEN 3
                      WHEN 'cancelled' THEN 4 END,
          order_id
LIMIT  12;
Without ORDER BY there is no order. A result that "looks sorted" is a coincidence of the current plan and will change. If order matters, say so explicitly.

LIMIT and OFFSET

LIMIT  n            -- at most n rows          (Postgres, MySQL, SQLite)
OFFSET m            -- skip the first m rows
FETCH FIRST n ROWS ONLY   -- the ANSI spelling; Postgres supports both
-- page 3, 5 rows per page  →  skip 10, take 5
SELECT emp_name, salary
FROM   employees
ORDER  BY salary DESC, emp_id      -- tie-break makes paging STABLE
LIMIT  5 OFFSET 10;
Paging without a unique tie-break is broken. With ties in salary, two pages can show the same person, or miss one. Always append a unique column to ORDER BY.
"How would you paginate a million rows?" OFFSET gets slower the deeper you go — the database still walks every skipped row. The senior answer is keyset (cursor) pagination: remember the last row you saw and use WHERE (salary, emp_id) < (:last_salary, :last_id).
-- keyset pagination: no OFFSET, uses the index, constant speed at any depth
SELECT emp_name, salary, emp_id
FROM   employees
WHERE  (salary, emp_id) < (150000, 6)     -- row-value comparison
ORDER  BY salary DESC, emp_id DESC
LIMIT  5;

JOINs

A join combines rows from two tables. Mentally: take every possible pairing, then keep the pairs where ON is true. (The database is far cleverer than that, but the mental model is exact.)

The syntax

FROM left_table  L
[INNER | LEFT [OUTER] | RIGHT [OUTER] | FULL [OUTER] | CROSS] JOIN right_table R
     ON  L.key = R.key          -- any boolean condition, not just equality
   | USING (key)                -- shorthand when the column name is identical
   | (CROSS JOIN takes no ON)

OUTER is optional noise: LEFT JOIN ≡ LEFT OUTER JOIN.

The five kinds

JoinKeepsUse it when
INNER JOINonly rows matching on both sidesyou want confirmed pairs
LEFT JOINall left rows + matches; NULLs where none"all customers, with their orders if any"
RIGHT JOINall right rows + matchesrare — flip the tables and use LEFT
FULL OUTER JOINeverything from both sidesreconciling two systems
CROSS JOINevery combination (Cartesian product)date spines, generating grids

See all of them on the same data. 14 customers, 11 of whom have orders:

SELECT 'INNER'  AS join_type, COUNT(*) AS rows, COUNT(DISTINCT c.cust_id) AS customers
FROM   customers c INNER JOIN orders o ON o.cust_id = c.cust_id
UNION ALL
SELECT 'LEFT',  COUNT(*), COUNT(DISTINCT c.cust_id)
FROM   customers c LEFT  JOIN orders o ON o.cust_id = c.cust_id
UNION ALL
SELECT 'FULL',  COUNT(*), COUNT(DISTINCT c.cust_id)
FROM   customers c FULL  JOIN orders o ON o.cust_id = c.cust_id;
-- LEFT keeps the 3 order-less customers (as NULL rows); INNER drops them.
-- LEFT JOIN showing the NULLs explicitly
SELECT c.cust_name, c.segment, o.order_id, o.order_date
FROM   customers c
LEFT   JOIN orders o ON o.cust_id = c.cust_id
WHERE  o.order_id IS NULL;        -- ← the 3 customers who never ordered

The single biggest JOIN trap: ON vs WHERE

On an outer join these are completely different. A condition in ON decides what counts as a match. The same condition in WHERE runs after the join and throws away the NULL-filled rows — silently converting your LEFT JOIN back into an INNER JOIN.

-- ✅ condition in ON: keeps all 14 customers; non-completed orders just become NULL
SELECT COUNT(*) AS rows_condition_in_on
FROM   customers c
LEFT   JOIN orders o ON o.cust_id = c.cust_id AND o.status = 'completed';

-- ❌ condition in WHERE: customers with no completed order VANISH. Now it's an INNER JOIN.
SELECT COUNT(*) AS rows_condition_in_where
FROM   customers c
LEFT   JOIN orders o ON o.cust_id = c.cust_id
WHERE  o.status = 'completed';
The rule. On an outer join, put conditions about the optional table in ON. Put conditions about the preserved table in WHERE. The only WHERE condition on the optional table that is safe is IS NULL — and that is deliberate, because it is how you write an anti-join.

Anti-joins and semi-joins

Anti-join = "rows in A with no match in B". Semi-join = "rows in A that have at least one match in B, without duplicating A". Three ways each; know all of them.

-- ANTI-JOIN, three ways. All return the 2 never-ordered products.
SELECT product_name FROM products p                       -- 1. NOT EXISTS  (best: NULL-safe, fast)
WHERE  NOT EXISTS (SELECT 1 FROM order_items i WHERE i.product_id = p.product_id);

SELECT p.product_name FROM products p                     -- 2. LEFT JOIN … IS NULL
LEFT   JOIN order_items i ON i.product_id = p.product_id
WHERE  i.product_id IS NULL;

SELECT product_name FROM products                         -- 3. NOT IN  ⚠ breaks on NULLs
WHERE  product_id NOT IN (SELECT product_id FROM order_items);
-- SEMI-JOIN: customers who ordered at least once — WITHOUT row multiplication
SELECT c.cust_name
FROM   customers c
WHERE  EXISTS (SELECT 1 FROM orders o WHERE o.cust_id = c.cust_id)
ORDER  BY c.cust_name;
-- Compare: an INNER JOIN would return one row PER ORDER, needing DISTINCT to fix.

Self-joins

Join a table to itself with two aliases. The standard hierarchy question.

-- every employee next to their manager  (LEFT JOIN keeps the CEO, who has none)
SELECT e.emp_name    AS employee,
       e.salary      AS emp_salary,
       m.emp_name    AS manager,
       m.salary      AS mgr_salary
FROM   employees e
LEFT   JOIN employees m ON m.emp_id = e.manager_id
ORDER  BY m.emp_name NULLS FIRST, e.emp_name;
-- classic: employees who earn MORE than their manager
SELECT e.emp_name AS employee, e.salary, m.emp_name AS manager, m.salary AS manager_salary
FROM   employees e
JOIN   employees m ON m.emp_id = e.manager_id
WHERE  e.salary > m.salary;

USING, NATURAL, and why to avoid one of them

SELECT o.order_id, c.cust_name          -- USING: column must be named identically in both
FROM   orders o JOIN customers c USING (cust_id)
LIMIT  5;
Never use NATURAL JOIN. It joins on every column that shares a name — including created_at or id columns you forgot about. Add a column to either table later and the query silently changes meaning. Say this in an interview and you sound experienced.

USING also merges the joined column into one, which matters for SELECT *.

Non-equi joins

ON takes any boolean condition, not just =. Range joins are common in interviews (banding, effective-dated records).

-- band every employee by joining on a RANGE
WITH bands(label, lo, hi) AS (
    VALUES ('junior', 0, 99999), ('mid', 100000, 129999),
           ('senior', 130000, 174999), ('executive', 175000, 999999)
)
SELECT e.emp_name, e.salary, b.label
FROM   employees e
JOIN   bands b ON e.salary BETWEEN b.lo AND b.hi
ORDER  BY e.salary DESC;

Joining three or more tables, and the double-count trap

-- ⚠ WRONG: joining two independent child tables multiplies their rows together
SELECT COUNT(*) AS inflated
FROM   orders o
JOIN   order_items oi ON oi.order_id = o.order_id
JOIN   web_events  w  ON w.cust_id   = o.cust_id;    -- rows = items × events

-- ✅ RIGHT: aggregate each child SEPARATELY, then join the summaries
SELECT c.cust_name,
       COALESCE(i.revenue, 0)  AS revenue,
       COALESCE(e.events, 0)   AS events
FROM   customers c
LEFT   JOIN (SELECT o.cust_id, SUM(oi.line_total) AS revenue
             FROM   orders o JOIN order_items oi ON oi.order_id = o.order_id
             WHERE  o.status = 'completed'
             GROUP  BY o.cust_id) i ON i.cust_id = c.cust_id
LEFT   JOIN (SELECT cust_id, COUNT(*) AS events
             FROM   web_events GROUP BY cust_id) e ON e.cust_id = c.cust_id
ORDER  BY revenue DESC NULLS LAST;
Remember the shape: "aggregate first, then join" — never "join everything, then aggregate" — whenever two child tables hang off the same parent.

Set operations

Joins combine tables side by side (more columns). Set operations stack them on top of each other (more rows).

UNION, INTERSECT, EXCEPT

query1 UNION     query2    -- all rows from both, DUPLICATES REMOVED
query1 UNION ALL query2    -- all rows from both, duplicates KEPT   ← faster
query1 INTERSECT query2    -- rows in both
query1 EXCEPT    query2    -- rows in query1 that are not in query2

Three rules: both sides need the same number of columns; matching columns need compatible types; column names come from the first query. A single ORDER BY at the very end sorts the combined result.

SELECT cust_name AS name, 'customer' AS kind FROM customers WHERE country = 'India'
UNION ALL
SELECT emp_name,          'employee'         FROM employees WHERE dept_id = 2
ORDER  BY kind, name;      -- ORDER BY belongs to the WHOLE result, once, at the end
-- UNION removes duplicates; UNION ALL does not. Count the difference.
SELECT COUNT(*) AS with_union     FROM (SELECT country FROM customers UNION     SELECT country FROM customers) u;
SELECT COUNT(*) AS with_union_all FROM (SELECT country FROM customers UNION ALL SELECT country FROM customers) u;
Default to UNION ALL. UNION must sort or hash everything to find duplicates, which costs real time on big tables. Use plain UNION only when you actually need de-duplication. Interviewers ask this specifically.
-- INTERSECT / EXCEPT: which cities have customers but no employees, and vice versa
SELECT city FROM customers WHERE city IS NOT NULL
EXCEPT
SELECT location FROM departments
ORDER  BY city;
Set operations compare whole rows and treat NULLs as equal — unlike =. That makes EXCEPT a neat way to diff two tables, including their NULLs.

Correlated subqueries — the concept interviewers probe

A subquery is correlated when it references a column from the outer query. That means it cannot be evaluated once; conceptually it re-runs for every outer row.

SELECT …
FROM   outer_table o
WHERE  … (SELECT … FROM inner_table i WHERE i.key = o.key) …
--                                              ↑ reference to the OUTER row
--                                                = correlated
-- each employee vs their OWN department's average — the inner query depends on e.dept_id
SELECT e.emp_name, e.dept_id, e.salary,
       (SELECT ROUND(AVG(e2.salary))
        FROM   employees e2
        WHERE  e2.dept_id = e.dept_id) AS dept_avg      -- ← correlated
FROM   employees e
WHERE  e.salary > (SELECT AVG(e2.salary)
                   FROM   employees e2
                   WHERE  e2.dept_id = e.dept_id)       -- ← correlated
ORDER  BY e.dept_id, e.salary DESC;
Say this: "That's a correlated subquery — it references the outer row, so logically it runs per row. A window function (AVG(salary) OVER (PARTITION BY dept_id)) does the same job in one pass and is usually faster." That comparison is exactly what they're listening for.
-- the SAME answer with a window function: one pass, no correlation
SELECT emp_name, dept_id, salary, dept_avg
FROM  (SELECT emp_name, dept_id, salary,
              ROUND(AVG(salary) OVER (PARTITION BY dept_id)) AS dept_avg
       FROM   employees) t
WHERE  salary > dept_avg
ORDER  BY dept_id, salary DESC;

EXISTS vs IN vs JOIN — which to reach for

GoalUseWhy
"has at least one related row"EXISTSstops at the first match; never duplicates rows; NULL-safe
"has none"NOT EXISTSNULL-safe, unlike NOT IN
"value is in this short fixed list"INreadable
"I need columns from the other table"JOINonly a join can return them
On performance: in modern PostgreSQL the planner rewrites IN, EXISTS and semi-joins into the same plan most of the time, so pick for correctness and readability. The one real difference that never goes away is NOT IN's NULL behaviour — that's a correctness issue, not a speed one.

LATERAL — a subquery that can see the row beside it

A normal subquery in FROM cannot reference other FROM items. LATERAL lets it — which makes "top N per group" trivial. (SQL Server spells this CROSS APPLY / OUTER APPLY.)

-- the 2 largest line items for each of the top customers
SELECT c.cust_name, t.product_id, t.line_total
FROM   customers c
CROSS  JOIN LATERAL (
         SELECT oi.product_id, oi.line_total
         FROM   orders o
         JOIN   order_items oi ON oi.order_id = o.order_id
         WHERE  o.cust_id = c.cust_id           -- ← sees c, only possible with LATERAL
         ORDER  BY oi.line_total DESC
         LIMIT  2
       ) t
ORDER  BY c.cust_name, t.line_total DESC;

CTEs & recursive CTEs

A CTE ("Common Table Expression", the WITH clause) is a named temporary result you define at the top and use below. It is the single biggest readability upgrade available to you.

Syntax and why it beats nesting

WITH name1 AS (
    SELECT …
), name2 AS (               -- ← comma between CTEs, none after the last
    SELECT … FROM name1     -- a CTE may use any CTE defined ABOVE it
)
SELECT … FROM name2;        -- the main query MUST follow
WITH completed AS (
    SELECT o.order_id, o.cust_id, o.order_date
    FROM   orders o
    WHERE  o.status = 'completed'
), revenue AS (
    SELECT c.cust_id, SUM(oi.line_total) AS revenue, COUNT(DISTINCT c.order_id) AS orders
    FROM   completed c
    JOIN   order_items oi ON oi.order_id = c.order_id
    GROUP  BY c.cust_id
)
SELECT cu.cust_name, cu.country, r.orders, ROUND(r.revenue, 2) AS revenue
FROM   revenue r
JOIN   customers cu ON cu.cust_id = r.cust_id
ORDER  BY r.revenue DESC
LIMIT  10;
Use CTEs to narrate your answer. Naming each step (completed, revenue) lets you talk the interviewer through your logic one block at a time. It reads far better than three levels of nested brackets, and it is much easier to debug — run each CTE on its own.
CTE vs subquery vs temp table. A CTE is scoped to one statement and stores nothing. A derived table is the same thing without a name. A temp table persists for the session and can be indexed — reach for it when the same intermediate result is needed by several statements or is very large.

MATERIALIZED / NOT MATERIALIZED

Since PG 12 the planner may inline a CTE into the outer query. Occasionally you want to force it.

WITH x AS MATERIALIZED     ( … )   -- compute once, store it
WITH x AS NOT MATERIALIZED ( … )   -- always inline, let the planner optimise through it
Before PG 12 a CTE was always an optimisation fence. If someone says "CTEs are slow in Postgres", they are remembering pre-12 behaviour — worth knowing, and worth correcting politely.

Recursive CTEs

For hierarchies (org charts, categories, graphs) and for generating series. A recursive CTE has exactly two parts joined by UNION ALL.

WITH RECURSIVE cte AS (
    SELECT …                    -- ANCHOR: the starting rows, runs once
    UNION ALL
    SELECT …                    -- RECURSIVE TERM: refers to `cte`, runs again and again
    FROM   source JOIN cte ON …
    WHERE  stop_condition       -- MUST eventually return no rows, or it never ends
)
SELECT * FROM cte;
-- the org chart, with depth and a readable path
WITH RECURSIVE org AS (
    SELECT emp_id, emp_name, manager_id,
           1                     AS level,
           emp_name::text        AS path
    FROM   employees
    WHERE  manager_id IS NULL                     -- ANCHOR: the CEO
    UNION ALL
    SELECT e.emp_id, e.emp_name, e.manager_id,
           o.level + 1,
           o.path || ' > ' || e.emp_name
    FROM   employees e
    JOIN   org o ON e.manager_id = o.emp_id        -- RECURSIVE: join back to the CTE
)
SELECT level, REPEAT('    ', level - 1) || emp_name AS org_chart, path
FROM   org
ORDER  BY path;
-- generate a series without generate_series()  (the portable trick)
WITH RECURSIVE n(x) AS (
    SELECT 1
    UNION ALL
    SELECT x + 1 FROM n WHERE x < 12        -- ← the stop condition
)
SELECT x, TO_CHAR(DATE '2024-01-01' + (x-1) * INTERVAL '1 month', 'YYYY-MM') AS month
FROM   n;
Infinite recursion. Forget the WHERE stop condition, or have a cycle in your data, and it runs forever. For graphs that may contain cycles, carry an array of visited ids and add WHERE NOT e.id = ANY(o.visited). Postgres 14+ also has a CYCLE clause.
Why UNION ALL and not UNION? UNION would de-duplicate at every step, which is slower and can mask legitimate repeated values. Use UNION only as a crude cycle guard.

Data-modifying CTEs

Postgres lets INSERT/UPDATE/DELETE … RETURNING act as a CTE — how you move rows between tables atomically.

DROP TABLE IF EXISTS demo_archive;
CREATE TABLE demo_archive (order_id integer, status text, archived_at timestamptz DEFAULT now());

WITH moved AS (
    DELETE FROM orders
    WHERE  status = 'cancelled'
    RETURNING order_id, status
)
INSERT INTO demo_archive (order_id, status)
SELECT order_id, status FROM moved
RETURNING order_id, status;
-- Reset the database afterwards to restore the cancelled orders.

Window functions

The highest-leverage topic on this page for an analyst role. If you are shaky anywhere, be shaky somewhere else.

The core idea

GROUP BY collapses rows: 16 employees become 3 department rows. A window function keeps every row and adds a value computed from a set of related rows — its "window".

-- GROUP BY: 3 rows out
SELECT dept_id, ROUND(AVG(salary)) AS dept_avg FROM employees WHERE dept_id IS NOT NULL GROUP BY dept_id;

-- WINDOW: all 16 rows out, each carrying its department average
SELECT emp_name, dept_id, salary,
       ROUND(AVG(salary) OVER (PARTITION BY dept_id)) AS dept_avg,
       salary - ROUND(AVG(salary) OVER (PARTITION BY dept_id)) AS vs_dept
FROM   employees
ORDER  BY dept_id NULLS LAST, salary DESC;

The full syntax

function(args) OVER (
    [PARTITION BY col, …]      -- split rows into independent groups. No PARTITION = one big group
    [ORDER BY col, …]          -- order rows WITHIN each partition
    [frame_clause]             -- which rows around the current one to include
)

frame_clause :=
    { ROWS | RANGE | GROUPS } BETWEEN frame_start AND frame_end [EXCLUDE …]

frame_start / frame_end :=
    UNBOUNDED PRECEDING     -- first row of the partition
  | n PRECEDING             -- n rows (ROWS) or n units of value (RANGE) back
  | CURRENT ROW
  | n FOLLOWING
  | UNBOUNDED FOLLOWING     -- last row of the partition
The default frame is the #1 window-function trap.
• With no ORDER BY → the frame is the whole partition.
• With an ORDER BY → the frame silently becomes RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW.
So SUM(x) OVER (ORDER BY d) is a running total, not a grand total — and LAST_VALUE(x) OVER (ORDER BY d) returns the current row, not the last one.
-- watch the default frame bite, and the fix
SELECT order_id, order_date,
       SUM(1)          OVER (ORDER BY order_date)                       AS running_count,
       SUM(1)          OVER ()                                          AS grand_total,
       LAST_VALUE(order_id) OVER (ORDER BY order_date)                  AS last_value_WRONG,
       LAST_VALUE(order_id) OVER (ORDER BY order_date
                                  ROWS BETWEEN UNBOUNDED PRECEDING
                                           AND UNBOUNDED FOLLOWING)     AS last_value_RIGHT
FROM   orders
ORDER  BY order_date
LIMIT  10;
ROWS vs RANGE. ROWS counts physical rows. RANGE counts values — all rows with the same ORDER BY value (peers) are included together. With duplicate dates, ROWS and RANGE give different running totals. When in doubt, write ROWS — it's what people usually mean.

The employee salaries contain deliberate ties, so all three differ. This is a guaranteed interview question:

SELECT emp_name, salary,
       ROW_NUMBER() OVER (ORDER BY salary DESC) AS row_number,
       RANK()       OVER (ORDER BY salary DESC) AS rank,
       DENSE_RANK() OVER (ORDER BY salary DESC) AS dense_rank
FROM   employees
ORDER  BY salary DESC;
-- ranking WITHIN each department
SELECT dept_id, emp_name, salary,

LAG and LEAD — comparing to the previous or next row

LAG (col [, offset [, default]]) OVER (PARTITION BY … ORDER BY …)   -- look BACK
LEAD(col [, offset [, default]]) OVER (PARTITION BY … ORDER BY …)   -- look FORWARD
-- offset defaults to 1; default is what to return when there is no such row (else NULL)
-- month-over-month revenue growth: the single most common analyst question
WITH monthly AS (
    SELECT DATE_TRUNC('month', o.order_date)::date AS month,
           SUM(oi.line_total)                      AS revenue
    FROM   orders o
    JOIN   order_items oi ON oi.order_id = o.order_id
    WHERE  o.status = 'completed'
    GROUP  BY 1
)
SELECT month,
       ROUND(revenue, 2)                                        AS revenue,
       ROUND(LAG(revenue) OVER (ORDER BY month), 2)             AS prev_month,
       ROUND(revenue - LAG(revenue) OVER (ORDER BY month), 2)   AS change,
       ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY month))
             / NULLIF(LAG(revenue) OVER (ORDER BY month), 0), 1) AS pct_growth
FROM   monthly
ORDER  BY month;
Note NULLIF(…, 0) guarding the division, and that the first month's pct_growth is correctly NULL rather than an error. Both details get noticed.

FIRST_VALUE, LAST_VALUE, NTH_VALUE

SELECT dept_id, emp_name, salary,
       FIRST_VALUE(emp_name) OVER w AS highest_paid_in_dept,
       LAST_VALUE(emp_name)  OVER w AS lowest_paid_in_dept,
       NTH_VALUE(emp_name,2) OVER w AS second_highest
FROM   employees
WHERE  dept_id IS NOT NULL
WINDOW w AS (PARTITION BY dept_id ORDER BY salary DESC
             ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING)
ORDER  BY dept_id, salary DESC;
The named WINDOW clause lets you define the spec once and reuse it. It sits between HAVING and ORDER BY. Using it shows fluency — and here it is load-bearing, because all three functions need the same explicit full frame.

Running totals, moving averages, share of total

WITH daily AS (
    SELECT o.order_date, SUM(oi.line_total) AS revenue
    FROM   orders o JOIN order_items oi ON oi.order_id = o.order_id
    WHERE  o.status = 'completed'
    GROUP  BY o.order_date
)
SELECT order_date,
       ROUND(revenue, 2) AS revenue,
       ROUND(SUM(revenue) OVER (ORDER BY order_date), 2)                  AS running_total,
       ROUND(AVG(revenue) OVER (ORDER BY order_date
                                ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 2) AS moving_avg_3,
       ROUND(100.0 * revenue / SUM(revenue) OVER (), 2)                   AS pct_of_total
FROM   daily
ORDER  BY order_date;

The universal workaround: compute the window value in a CTE or subquery, then filter it in the outer query. This is the shape for every "top N per group" question.
-- ❌ ERROR: window functions are not allowed in WHERE
SELECT emp_name, RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS r
FROM   employees
WHERE  RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) <= 2;
-- ✅ the fix: rank inside, filter outside. Top 2 earners per department.
WITH ranked AS (
    SELECT emp_name, dept_id, salary,
           RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS r
    FROM   employees
    WHERE  dept_id IS NOT NULL
)
SELECT dept_id, emp_name, salary, r
FROM   ranked
WHERE  r <= 2
ORDER  BY dept_id, r;

Windows run after GROUP BY — so you can combine them

A window function sees the grouped rows, which lets you aggregate and then rank in one query.

SELECT c.country,
       COUNT(DISTINCT o.order_id)                                  AS orders,
       ROUND(SUM(oi.line_total), 2)                                AS revenue,
       RANK() OVER (ORDER BY SUM(oi.line_total) DESC)              AS revenue_rank,
       ROUND(100.0 * SUM(oi.line_total) / SUM(SUM(oi.line_total)) OVER (), 1) AS pct_of_total
FROM   orders o
JOIN   customers   c  ON c.cust_id  = o.cust_id
JOIN   order_items oi ON oi.order_id = o.order_id
WHERE  o.status = 'completed'
GROUP  BY c.country
ORDER  BY revenue DESC;
That SUM(SUM(...)) OVER () looks strange but is exactly right: the inner SUM aggregates within each country, the outer windowed SUM totals across all the grouped rows. Being comfortable with this marks you out.

Interview patterns

Twelve shapes that cover most of what actually gets asked. Learn the shape, not the query — the table names change, the shape doesn't.

1 · Nth highest value — three ways

-- (a) DENSE_RANK: handles ties the way "3rd highest SALARY" usually means
WITH r AS (SELECT emp_name, salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rk FROM employees)
SELECT * FROM r WHERE rk = 3;

-- (b) OFFSET on distinct values: short, but silently wrong if you forget DISTINCT
SELECT DISTINCT salary FROM employees ORDER BY salary DESC OFFSET 2 LIMIT 1;

-- (c) correlated subquery: the classic no-window-functions answer
SELECT DISTINCT e.salary FROM employees e
WHERE  2 = (SELECT COUNT(DISTINCT e2.salary) FROM employees e2 WHERE e2.salary > e.salary);
Ask before you answer: "with ties, should two people on the same salary both count as 2nd, and is 3rd-highest by person or by distinct salary?" That question is the point of this problem — ROW_NUMBER, RANK and DENSE_RANK each answer a different version of it.

2 · Top N per group

WITH ranked AS (
    SELECT p.category, p.product_name, SUM(oi.line_total) AS revenue,
           ROW_NUMBER() OVER (PARTITION BY p.category ORDER BY SUM(oi.line_total) DESC) AS rn
    FROM   products p
    JOIN   order_items oi ON oi.product_id = p.product_id
    JOIN   orders o ON o.order_id = oi.order_id AND o.status = 'completed'
    GROUP  BY p.category, p.product_name
)
SELECT category, product_name, ROUND(revenue,2) AS revenue, rn
FROM   ranked WHERE rn <= 2
ORDER  BY category, rn;

3 · Finding duplicates

-- which rows appear more than once, and how many times
SELECT raw_email, raw_name, source, loaded_at, COUNT(*) AS copies
FROM   staging_signups
GROUP  BY raw_email, raw_name, source, loaded_at
HAVING COUNT(*) > 1;
-- duplicates by BUSINESS key only (same email, any spelling/case)
SELECT LOWER(raw_email) AS email, COUNT(*) AS rows, COUNT(DISTINCT raw_name) AS name_variants
FROM   staging_signups
GROUP  BY LOWER(raw_email)
HAVING COUNT(*) > 1
ORDER  BY rows DESC;

4 · De-duplication — keep one row per key

-- keep the MOST RECENT record per email, case-insensitively
WITH ranked AS (
    SELECT raw_email, raw_name, source, loaded_at,
           ROW_NUMBER() OVER (PARTITION BY LOWER(raw_email)
                              ORDER BY loaded_at DESC) AS rn
    FROM   staging_signups
)
SELECT raw_email, raw_name, source, loaded_at
FROM   ranked WHERE rn = 1
ORDER  BY raw_email;
Why ROW_NUMBER and not RANK here? Because you need exactly one survivor. RANK would keep every tied row and you'd still have duplicates.

5 · Running total & cumulative share

WITH m AS (
    SELECT DATE_TRUNC('month', o.order_date)::date AS month, SUM(oi.line_total) AS rev
    FROM   orders o JOIN order_items oi ON oi.order_id = o.order_id
    WHERE  o.status = 'completed' GROUP BY 1
)
SELECT month, ROUND(rev,2) AS revenue,
       ROUND(SUM(rev) OVER (ORDER BY month), 2)                        AS cumulative,
       ROUND(100.0 * SUM(rev) OVER (ORDER BY month) / SUM(rev) OVER (), 1) AS cum_pct
FROM   m ORDER BY month;

6 · Pivot — rows into columns

Postgres has no PIVOT keyword. Conditional aggregation is the pivot.

SELECT c.country,
       COUNT(*) FILTER (WHERE o.status = 'completed') AS completed,
       COUNT(*) FILTER (WHERE o.status = 'pending')   AS pending,
       COUNT(*) FILTER (WHERE o.status = 'cancelled') AS cancelled,
       COUNT(*) FILTER (WHERE o.status = 'refunded')  AS refunded,
       COUNT(*)                                       AS total
FROM   orders o JOIN customers c ON c.cust_id = o.cust_id
GROUP  BY c.country
ORDER  BY total DESC;
-- UNPIVOT: columns back into rows, using a VALUES list + CROSS JOIN LATERAL
SELECT d.dept_name, m.metric, m.value
FROM   departments d
CROSS  JOIN LATERAL (VALUES ('budget', d.budget), ('budget_in_lakhs', d.budget/100000)) AS m(metric, value)
ORDER  BY d.dept_name, m.metric;

7 · Gaps and islands — consecutive runs

The trick: date − ROW_NUMBER() is constant within a consecutive run. Group by that constant.

WITH d AS (
    SELECT DISTINCT event_at::date AS dt
    FROM   web_events WHERE cust_id = 1 AND event_type = 'page_view'
), grouped AS (
    SELECT dt, dt - (ROW_NUMBER() OVER (ORDER BY dt))::int AS island   -- ← the trick
    FROM   d
)
SELECT MIN(dt) AS run_start, MAX(dt) AS run_end, COUNT(*) AS consecutive_days
FROM   grouped
GROUP  BY island
ORDER  BY run_start;
Expect three runs: 1–5 March (5 days), 9–11 March (3 days), and 20 March (1 day). The same shape answers "longest login streak" and "consecutive winning days".

8 · Funnel conversion

WITH f AS (
    SELECT COUNT(DISTINCT session_id) FILTER (WHERE event_type='page_view')   AS viewed,
           COUNT(DISTINCT session_id) FILTER (WHERE event_type='add_to_cart') AS carted,
           COUNT(DISTINCT session_id) FILTER (WHERE event_type='checkout')    AS checked_out,
           COUNT(DISTINCT session_id) FILTER (WHERE event_type='purchase')    AS purchased
    FROM   web_events
)
SELECT viewed, carted, checked_out, purchased,
       ROUND(100.0*carted      /NULLIF(viewed,0),     1) AS view_to_cart_pct,
       ROUND(100.0*checked_out /NULLIF(carted,0),     1) AS cart_to_checkout_pct,
       ROUND(100.0*purchased   /NULLIF(checked_out,0),1) AS checkout_to_purchase_pct,
       ROUND(100.0*purchased   /NULLIF(viewed,0),     1) AS overall_pct
FROM   f;

9 · Cohort retention

WITH cohort AS (          -- each customer's first completed order month
    SELECT o.cust_id, MIN(DATE_TRUNC('month', o.order_date))::date AS cohort_month
    FROM   orders o WHERE o.status='completed' GROUP BY o.cust_id
), activity AS (          -- every month each customer was active
    SELECT DISTINCT o.cust_id, DATE_TRUNC('month', o.order_date)::date AS active_month
    FROM   orders o WHERE o.status='completed'
)
SELECT c.cohort_month,
       (EXTRACT(YEAR FROM a.active_month)*12 + EXTRACT(MONTH FROM a.active_month))
     - (EXTRACT(YEAR FROM c.cohort_month)*12 + EXTRACT(MONTH FROM c.cohort_month)) AS months_since,
       COUNT(DISTINCT a.cust_id) AS customers
FROM   cohort c JOIN activity a ON a.cust_id = c.cust_id
GROUP  BY 1, 2
ORDER  BY 1, 2;

10 · Median and percentiles

SELECT PERCENTILE_CONT(0.5)  WITHIN GROUP (ORDER BY salary) AS median_interpolated,
       PERCENTILE_DISC(0.5)  WITHIN GROUP (ORDER BY salary) AS median_actual_value,
       PERCENTILE_CONT(0.25) WITHIN GROUP (ORDER BY salary) AS p25,
       PERCENTILE_CONT(0.90) WITHIN GROUP (ORDER BY salary) AS p90,
       MODE() WITHIN GROUP (ORDER BY salary)                AS most_common
FROM   employees;
PERCENTILE_CONT interpolates between the two middle values (a real median); PERCENTILE_DISC returns an actual value from the data. If asked for median without these functions, the fallback is ROW_NUMBER from both ends and average the middle one or two.

11 · Filling date gaps with a spine

WITH spine AS (
    SELECT g::date AS month
    FROM   generate_series(DATE '2024-01-01', DATE '2024-06-01', INTERVAL '1 month') g
), actual AS (
    SELECT DATE_TRUNC('month', o.order_date)::date AS month, SUM(oi.line_total) AS rev
    FROM   orders o JOIN order_items oi ON oi.order_id=o.order_id
    WHERE  o.status='completed' AND o.channel='partner'
    GROUP  BY 1
)
SELECT s.month, COALESCE(ROUND(a.rev,2), 0) AS partner_revenue
FROM   spine s LEFT JOIN actual a ON a.month = s.month     -- LEFT JOIN from the SPINE
ORDER  BY s.month;
Why this matters: a plain GROUP BY month simply omits months with no sales, so a chart shows a straight line instead of a hole. Always LEFT JOIN from the spine.

12 · Year-over-year / period comparison without a self-join

WITH m AS (
    SELECT DATE_TRUNC('month', o.order_date)::date AS month,
           COUNT(DISTINCT o.order_id) AS orders
    FROM   orders o WHERE o.status='completed' GROUP BY 1
)
SELECT month, orders,
       LAG(orders, 1)  OVER (ORDER BY month) AS prev_month,
       LAG(orders, 3)  OVER (ORDER BY month) AS three_months_ago,
       orders - LAG(orders,1) OVER (ORDER BY month) AS mom_change,
       ROUND(AVG(orders) OVER (ORDER BY month ROWS BETWEEN 2 PRECEDING AND CURRENT ROW),2) AS ma3
FROM   m ORDER BY month;

Schema design & normalization

Keys

KeyDefinition
Super keyany column set that uniquely identifies a row
Candidate keya minimal super key — remove any column and uniqueness breaks
Primary keythe candidate key you chose. Unique + NOT NULL, one per table
Alternate keythe candidate keys you didn't choose (enforce with UNIQUE)
Composite keya key made of 2+ columns
Foreign keya column referencing a key in another table
Surrogate keya meaningless generated id (emp_id)
Natural keya real-world identifier (email, ISBN)
"Surrogate or natural?" Surrogate, usually: real-world identifiers change (people change email and surname), and a changing PK cascades everywhere. Keep the natural key too, as a UNIQUE constraint — you get stability and the business rule.

Normal forms — with the one-line version of each

FormRuleViolation looks like
1NFAtomic values; no repeating groups or lists in a cellphones = '555-1, 555-2' or columns phone1, phone2, phone3
2NF1NF + no partial dependency on part of a composite keyIn (order_id, product_id), storing product_name — it depends on product_id alone
3NF2NF + no transitive dependency (non-key → non-key)Storing dept_name in employees: it depends on dept_id, not on emp_id
BCNF3NF + every determinant is a candidate keyRare overlapping-candidate-key cases
4NFBCNF + no multi-valued dependenciesIndependent lists (skills, languages) crammed into one table
The memory hook: "the key, the whole key, and nothing but the key, so help me Codd." 1NF = atomic. 2NF = the whole key. 3NF = nothing but the key.
Why denormalize? Normalization removes update anomalies and redundancy — ideal for OLTP writes. Analytics reads pay for it in joins. So warehouses deliberately denormalize into star schemas: a central fact table (one row per event, e.g. order_items) surrounded by dimension tables (customers, products, dates). A snowflake schema normalizes the dimensions further. Say "it's a trade-off between write integrity and read speed" and you've answered the question.

Relationships

  • One-to-one — FK plus a UNIQUE on it. Usually a sign the tables should be merged.
  • One-to-many — FK on the "many" side. (orders.cust_id.) The common case.
  • Many-to-many — needs a junction table holding two FKs, with a composite PK across them. order_items is exactly this between orders and products.
Slowly Changing Dimensions — how a warehouse tracks history. Type 1: overwrite, no history. Type 2: new row per change with valid_from/valid_to and an is_current flag — the one worth knowing. Type 3: keep a "previous value" column.

Indexes & performance

What an index is

A sorted side structure (usually a B-tree) mapping values to row locations. It turns "read all 10 million rows" into "walk down a few levels of a tree". The cost: every INSERT/UPDATE/ DELETE must also maintain it, and it takes disk. Indexes make reads faster and writes slower. That sentence answers a lot of questions.

CREATE INDEX        idx_name ON t (col);                    -- plain B-tree
CREATE INDEX        idx_name ON t (a, b);                   -- composite: ORDER MATTERS
CREATE UNIQUE INDEX idx_name ON t (col);                    -- also enforces uniqueness
CREATE INDEX        idx_name ON t (col) WHERE status='open';-- partial: smaller, targeted
CREATE INDEX        idx_name ON t (LOWER(email));           -- expression index
CREATE INDEX        idx_name ON t USING GIN (tags);         -- for arrays / jsonb / full-text
DROP INDEX idx_name;

Index the right things

  • Columns in WHERE, JOIN … ON, ORDER BY, GROUP BY.
  • Every foreign key — Postgres does not index FKs automatically, and unindexed FKs make parent deletes crawl.
  • High-selectivity columns (many distinct values). An index on a boolean rarely helps — unless it's partial.

Don't index tiny tables, low-selectivity columns, or write-heavy columns that are never filtered. And don't add an index the query can't use:

Sargability — what silently disables your index

"Sargable" = Search-ARGument-able. If you wrap the column in a function or arithmetic, the index on that column becomes unusable.

The rule in one line: keep the indexed column bare on one side of the operator, and do the maths on the other side.

Composite indexes and the leftmost-prefix rule

An index on (cust_id, order_date) can serve queries filtering on cust_id, or on cust_id AND order_date — but not order_date alone. Think of a phone book sorted by (surname, first name): useless for finding all the Rahuls.

Ordering heuristic: equality columns first, range columns last. For WHERE cust_id = 7 AND order_date > … the right index is (cust_id, order_date), not the reverse.

Why is this query slow? — a checklist to say out loud

  1. Run EXPLAIN ANALYZE — never guess.
  2. Is there a Seq Scan on a large table with a selective WHERE? Missing index.
  3. Is the WHERE sargable? A function on the column disables the index.
  4. Are estimates far from actuals? Stale statistics — run ANALYZE.
  5. Is the join fanning out? Check the grain; aggregate before joining.
  6. Is SELECT * dragging back columns nobody uses, preventing an index-only scan?
  7. Is DISTINCT or UNION hiding a join bug? De-duplication is often a symptom.
  8. Deep OFFSET? Switch to keyset pagination.
  9. OR across different columns? Sometimes two UNION ALL branches index better.
  10. Could this be precomputed — a materialized view or a summary table?

Locks, deadlocks, and MVCC

MVCC (Multi-Version Concurrency Control) is how Postgres avoids read locks: every writer creates a new row version, so readers never block writers and writers never block readers. That single sentence answers "how does Postgres handle concurrency?".

A deadlock is two transactions each holding what the other needs. Postgres detects it and kills one. Prevention: always acquire locks in the same order across your application, keep transactions short, and don't hold one open while waiting on a human.

Triggers

Code that fires automatically on INSERT/UPDATE/DELETE. In Postgres a trigger calls a function returning trigger.

CREATE TABLE IF NOT EXISTS demo_audit (
    audit_id  integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku       text, old_qty integer, new_qty integer, changed_at timestamptz DEFAULT now()
);

CREATE OR REPLACE FUNCTION log_stock_change() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
    INSERT INTO demo_audit (sku, old_qty, new_qty) VALUES (OLD.sku, OLD.qty, NEW.qty);
    RETURN NEW;                       -- BEFORE triggers must return a row
END; $$;

DROP TRIGGER IF EXISTS trg_stock ON demo_stock;
CREATE TRIGGER trg_stock AFTER UPDATE ON demo_stock
FOR EACH ROW EXECUTE FUNCTION log_stock_change();

UPDATE demo_stock SET qty = qty + 1 WHERE sku = 'A1';
SELECT * FROM demo_audit;
OLD and NEW are the row before and after. BEFORE triggers can modify NEW; AFTER triggers cannot. Use triggers sparingly — they are invisible from the application and make debugging hard.

Interview playbook

How to answer a query question out loud

  1. Restate it. "So you want one row per customer, with their total completed revenue, including customers who have never ordered — is that right?" This catches half of all misunderstandings.
  2. Ask the clarifying questions (list below). Interviewers score this explicitly.
  3. Say the grain. "One row per customer per month."
  4. Name your steps before writing. "Filter to completed, aggregate to customer level, then left join back so I keep the zero-revenue customers."
  5. Write it in CTEs, one named step at a time. Easy to follow, easy to fix.
  6. Check the edges yourself: NULLs, ties, divide-by-zero, empty groups, duplicates.
  7. Offer the trade-off. "This works; on a big table I'd add an index on orders(cust_id, order_date)."

The clarifying questions that earn marks

  • Should customers with no orders appear, with zero — or be excluded?
  • Do cancelled and refunded orders count toward revenue?
  • On a tie, do both rows rank the same — and is "3rd highest" by person or by distinct value?
  • Is revenue before or after discount? Gross or net of refunds?
  • Is the date column a date or a timestamp? Which time zone?
  • Should months with no activity appear as zero rows?
  • Can this table contain duplicates? What is the real business key?
  • How big is the table — do I need to care about performance?
